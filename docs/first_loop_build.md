**Built:** 24 Nov 2026, after Part 3 closed (sugarR rung PASS, gate upheld, signed off). **Code:** `repo/fresh/part2b/` (decoder, sensory channel, bridge protocol, brain worker, loop driver, sanity run, battery, probes, tests). **Gate:** LIGHT, with the K6 hard-stop rule. **What Part 2b had to prove** (FINAL-PLAN §4, Part 2b row): that a toy population decoder can carry activity out of the validated brain into the audited body, and a sensory event can carry information back — the loop running stably, end to end, with a decoder-only sanity run documented so decoder behaviour is never confused with brain behaviour. ## 1. The two findings that shaped the design

**Finding 1 — the sugar circuit's descending readouts are silent, and that is data, not a defect.** Before designing anything I counted spikes in the Part 3 validation output itself (`runs/part3-sugarR-200Hz/spikes.parquet`, 30 trials): under the validated sugar protocol, **aDN1, aDN2-left and aBN1 fire zero spikes in all 30 trials**, and the JON population fires zero (no mechanosensory input exists in that experiment). MN9 fires at 92.6 / 62.4 Hz. A decoder reading the DNs under sugar alone would output zero forever — the loop could never move, and no sensory event could ever occur. The reason is anatomical, not a bug: the Part 2 ID sets' only descending neurons are aDN1 and aDN2-left, which are the readouts of upstream's **Johnston's-organ (mechanosensory) experiments**, not of the feeding circuit (the reading log is explicit that upstream defines no brain-wide DN population; MN9 is a motor neuron, not a descending readout). So the minimal honest loop is built around the pathway those neurons actually belong to: **JON → aDN**, with the sugar stimulus kept on as the validated brain context and MN9 logged as the feeding readout (not decoded — decoding a motor neuron into a walking command would be exactly the kind of quiet substitution this project exists to avoid).

**Finding 2 — the frozen `Brain.run()` cannot be called twice, so the bridge holds its own Network.** `Brain.run()` constructs a fresh Brian2 `Network` on every call. Brian2 2.9 refuses to add already-simulated objects to a new Network ("neurongroup has already been simulated, cannot add it to the network… set its active flag to False instead" — the error names the intended mechanism). The bridge therefore builds **one persistent Network from the frozen Brain's own objects** (neurons, synapses, monitor, drives) and runs it in chunks. No frozen file changes; the scaffolding around the model is mine, the model is untouched. Probe 2 (§3) proves this scaffolding is dynamics-neutral.

## 2. The interface contract

- **Boundary:** two processes, because the pinned environments cannot coexist (brain: Brian2 2.9.0 / numpy 1.26.4; body: FlyGym 2.1.1 / MuJoCo 3.16.0 / numpy 2.5.5). The driver (body env) spawns the brain worker (brain env); they exchange one JSON object per line over the worker's stdin/stdout. The schema is a shared module (`part2b/protocol.py`), pinned by tests on both sides' behalf: replies must be in-order, complete, and non-negative, and the driver refuses anything else rather than manufacture a result from a malformed reply.
- **Chunk:** 100 ms of simulated time on both sides. Brain chunk = one `net.run(100 ms)` on the persistent Network; body chunk = 1,000 physics steps at the model's 1e-4 s timestep, the descending signal held constant across the chunk. Eon's 15 ms sync is the literature reference point (plan §4); 100 ms is chosen here because the readout is two neurons — a 15 ms window would hold 0–1 spikes and the rate estimate would be pure noise — and because chunk duration is one of the K6-adjustable interface parameters, not a model property. Probe 2 shows the choice costs nothing dynamically.
- **Latency, stated:** the signal that drives body chunk *k* is decoded from brain chunk *k*, whose sensory state was set by body chunk *k−1* — so sensory feedback carries exactly **one chunk (100 ms) of simulated latency**, plus the decoder filter's lag (τ = 0.2 s EMA, §4). Brain and body chunks run sequentially in wall-clock (measured over the battery: a full 20-chunk episode, worker start-up included, took 93–101 s wall — roughly 4–5 s per brain+body chunk pair at loop activity levels, the probes' compile costs already cached — **i.e. 46.5–50.5 s of wall clock per simulated second** for the closed episodes; the open control cost 34.5 s per simulated second, its brain chunks being cheaper with the JON drive mostly off); wall-clock latency is not part of the simulated system and is reported only as cost.
- **Failure behaviour:** any worker error, malformed reply, or dead process aborts the episode loudly (the episode is recorded as failed, never partially summarised as a success).

The worker therefore does a zero-duration warmup run with all drives active at start-up, paying the cost before the episode clock starts instead of inside a timed chunk.

## 4. The toy decoder (PROVISIONAL — replaced at Parts 4/5)

`part2b/decoder.py`, in full: pooled aDN1 + aDN2-left spike count per chunk → rate (summed spikes/second across the two-neuron set) → exponential moving average, τ = 0.2 s → clipped linear ramp, amplitude = clip((rate − 2 Hz)/(40 Hz − 2 Hz), 0, 1) → descending signal **(amplitude, amplitude)**.

- **Symmetric output is a honesty constraint, not laziness:** the extracted DN sets contain aDN1 (a single unpaired neuron) and aDN2-*left* only. There is no right-side DN to decode a left/right difference from; any asymmetric command would be invented. Straight walking is all this decoder can say.
- **Constants are chosen, not fitted** (2 Hz floor — just above the DNs' verified silence; 40 Hz saturation — the probes show sustained JON drive pools to ~46 Hz; τ = 0.2 s — two chunks of smoothing). They were fixed before the stability run and were **not** retuned on its outcome; Part 4/5 derive or fit their own on calibration data (§7.3 separation applies there).
- **Bridge-test properties** (plan §6.2 applied to the toy): zero input gives exactly zero command; the map is monotone and saturating; left always equals right. All pinned by tests.

## 5. The sensory channel (PROVISIONAL / CONSTRUCTED — binding specs at Part 4)

`part2b/sensory.py` + the rule in `run_loop.py`:

- The body reports one ground-contact flag per leg at every physics step (MuJoCo contact sensors via FlyGym). A **transition** is a leg's flag changing between steps. Standing still produces none once settled; stepping produces them continuously.
- **Rule:** ≥1 transition in body chunk *k* ⇒ the JON drive is on for brain chunk *k+1*. Contact *level* was rejected as the signal: a standing fly is in contact too, so a level could never demonstrate that body *events* re-enter the brain; transitions are events, are caused by movement, and stop when movement stops.
- **Bootstrap:** a standing fly generates no transitions, so the loop needs a first stimulus — each episode includes one scripted **touch pulse** (JON drive on for chunks 2–3, t = 0.2–0.4 s), an encoder-side stimulus event labelled scripted/constructed, exactly analogous to switching the sugar stimulus on. What happens after the pulse is the loop's own business: if walking starts, its footfalls sustain the JON drive; if it doesn't, the drive stops and the fly stands.
- **Control:** one episode runs open-loop (seed 4200): transitions are logged but never converted. The pulse is identical; only the feedback wire is cut. Whatever walking the pulse starts should die away — the contrast that shows the loop, not the pulse, sustaining closed-loop walking (an embryo of RQ-P3's closed-vs-open comparison, exploratory here).

## 7. Stability run — criteria first, then results

The criteria were fixed in `run_battery.py` before any episode ran: **C1** completion + finiteness (20/20 chunks, no NaN/Inf in any recorded body state); **C2** physical bounds (thorax height within (0, 3) mm, episode travel < 100 mm — explosion detectors); **C3** walking-while-active (mean travel in chunks at amplitude ≥ 0.5 exceeds mean travel at amplitude ≤ 0.05 by ≥ 0.3 mm, per closed episode; the 0.5 band is the decoder's own mid-ramp, set from its geometry and the probe rates); **C4** sensory re-entry (feedback-commanded chunks average ≥ 20 JON spikes; off chunks average 0, the Part 3-verified baseline, or ≤ a tenth of the feedback mean); **C5** closed-vs-open contrast, exploratory (open control's chunks-10–19 travel < half the closed episodes' mean). K6 is a C1/C2-class failure — the loop cannot run stably; C3–C5 failing with C1/C2 intact would be a weak scientific result, reported as such, not a K6 event and not a retuning licence.

The loop buys the whole episode. *(This paragraph's two figures were corrected and defined on 24 Nov 2026 under Reviewer 1's gate conditions (1)–(2); the original text said "the pulse alone buys ~0.5 s of walking" and left the 12.72 mm figure's mean unstated. See §10.)*

**Two observations recorded plainly, because they are part of the result:**

1. **The closed loop ignited itself one chunk before the scripted pulse.** Chunk 0 of every episode contains ~202 contact transitions — post-warmup settling: the body, placed at 0.8 mm and warmed up for 0.05 s, is still seating its legs when the episode starts, and contact flags flicker as it settles. In the closed episodes those genuine body events switched the JON drive on at chunk 1, the DNs were already warm (filtered rate 15.7 Hz) when the pulse arrived at chunk 2, and the pulse reinforced an already-closing loop rather than igniting a cold one. In the open episode the identical 202 settle transitions occurred (the body is deterministic; chunk 0 is byte-identical across arms) and were simply never converted. So the honest statement is: the scripted pulse is *a* sufficient bootstrap from cold (the control shows it recruiting the DNs from zero), but in the closed episodes the actual first feedback came from settling physics. Both bootstraps are body/brain events, not hidden code paths; the distinction matters for Part 4's stimulus design, where the settle transient should be waited out or baselined away before any stimulus is timed.
2. **The open episode's summary line "travel in signal-on chunks = 0.0 mm" is a band artifact, not zero walking:** its amplitude peaked at 0.72, so no chunk entered the ≥0.8 band the summary uses; the chunk table shows the brief walk explicitly. I am recording the artifact here rather than adjusting the summary code after the fact — the per-chunk data is the primary record, and it is unambiguous.

## 9. Deviations, failures, surprises

- **First toggle experiment failed by design error (mine):** I initially toggled drives across *fresh* Network objects, which Brian2 forbids for already-simulated objects. The error message itself named the correct mechanism; the persistent-Network design and Probe 1 are the result. Recorded because it is the reason the bridge looks the way it does.
- **The compile storm (§3)** was a surprise: ~10 min of gcc the first time the JON drives activated. It is a wall-clock cost only — compilation happens before any timestep runs, so no simulated quantity is affected — and the worker's zero-duration warmup moves it out of the timed chunks.
- **One test premise was wrong, and I fixed the test, not the code:** my first filter test fed the decoder a 40-spike chunk (400 Hz pooled — impossible for a two-neuron readout) and expected sub-saturation output. The decoder's arithmetic was right; the test's notion of a "loud chunk" was not. The test now uses 4 spikes and says why.
- **The settle transient (§7, observation 1)** was not predicted: I expected a standing fly to be transition-silent from chunk 0, and it is — but only after it finishes settling, which takes longer than the demos' 0.05 s warmup. It changed no outcome (the control arm absorbs it), but Part 4's specs inherit the lesson: stimulus timing must be referenced to a settled baseline, not to episode start.
- Nothing in the frozen model, the Part 3 outputs, or the audited body pathway was modified. No K6 event occurred in the probes or the run: every mechanism the loop needs was demonstrated working before the loop was assembled, and the assembled loop ran stably in all three seeds.

### 10.1 The "bit-for-bit" claim — re-verified by hash, with a qualification

The original probe 2 compared the single-run and chunked-run trains with `numpy.array_equal` in memory and archived only the spike counts (5,243 = 5,243) plus a boolean in `probe_results.json` — the trains themselves were never archived, so as archived the claim rested on the counts. Re-check (`probes/verify_chunk_equivalence.py`, `probes/diagnose_equivalence.py`; trains archived as `probes/equivalence_train_*.npz`, verdicts in `probes/equivalence_verification.json` and `probes/diagnose_equivalence_*.json`): each train is canonicalised — (FlyWire root ID, spike time) sorted by (time, root ID) — and fingerprinted with SHA-256 over the sorted int64 IDs followed by the sorted float64 times, in probe 2's exact configuration (seed 4105, sugar right at 200 Hz, 300 ms).

**Verdict: the claim stands, with a qualification the original probe could not see.** At a fixed build position, chunked and single runs are bit-for-bit identical — hash-equal, element-equal: build #1 in a fresh process gives SHA-256 `46bf581500a386f1b7b417ddd36afbafac1ddaf980cf43c0d4f7c3ad2096397b` (5,539 spikes) under both structures, reproduced across separate processes; builds #2 and #4 in one process give `71c8f5cd98d8c59b0ff11825367eee9b352697311105919fcbfa2aa3c1747d66` (5,243 spikes) under both structures. The qualification: **successive same-seed builds within one process alternate between two RNG streams** (the two trains above), so a build's train is a function of its position in the process as well as of (data, params, seed). Probe 2's two builds both landed on the 5,243 stream — its equality conclusion was correct, and its archived count is explained. Consequences, stated plainly: (i) the bridge is unaffected — the brain worker is a fresh process with exactly one build per episode, and at build #1 the chunked train *is* the single-run train, bit for bit; (ii) Part 3 is unaffected — its determinism check compared two separate single-build processes (bit-identical, as this finding predicts) and its trials used distinct seeds with distributional comparisons; (iii) the frozen model's build docstring ("a function of (data, params, seed, manipulations) and nothing else") is incomplete for repeated in-process builds — the frozen code is not edited for a docstring, so the correction lives here: **any future in-process multi-build comparison must compare builds at the same build position, or use fresh processes.** The mechanism of the alternation was not identified; the empirical fact is reproducible and is what the record needs. The brain worker's docstring repeats the unqualified bit-for-bit sentence; it is true at the worker's fixed build position, and this section is the qualification of record for it.

### 10.3 Descending-neuron bilaterality — aDN2 is a bilateral type; the set holds its left member only

Checked against every annotation-bearing source in the project data (condition (d)). First, what the v630 materialisation itself carries: **no annotation table** — the completeness file is (ID, Completed) and the connectivity file is (pre, post, count, sign); there are no cell-type or side columns to check against (Part 2's pin, `PART2-ID-SETS.md` §6, already established that the extracted identities rely on no annotation table). The annotation-bearing sources on disk are the upstream notebooks (the extraction source), the old build's independently transcribed constants, and the paper as read in the reading log. Against those:

- **aDN2 is a sided type, and the extracted neuron is its left member.** The source names it `id_DN2_l` — the `_l` is explicit. A right aDN2 exists in the v630 brain as anatomy; its root ID appears in **no** text source in the project: the upstream notebooks contain exactly two descending-neuron identifiers (`id_DN1_1`, `id_DN2_l` — verified by exhaustive search of both notebooks, 24 Nov 2026), and the old build's constants likewise carry only `DN2_L`.
- **Classification: not an extraction error, but an anatomical incompleteness, and the record now says which.** The extraction obligation was the populations the published experiments define, and the published JON experiments read out the left aDN2 only — nothing the extraction was charged with was missed. But the Part 2 set holds one member of a bilateral type, so Part 2b's symmetric decoder was forced by the *published readout*, not merely by an extraction choice: with only a left DN in hand, no left/right differential command could have been decoded honestly. Conversely, had the right aDN2 been identified, a differential readout would have been possible in principle — that is what changes if the set is completed, and it is a Part 4/5 design input, not a Part 2b defect.
- **Identifying the right aDN2 requires an annotation source the project does not have on disk.** It would need type+side assignments joined onto v630 root IDs; current annotation releases are v783-era and do not join onto v630 (the crosswalk problem already on record, `PART2-ID-SETS.md` §6). The right aDN2 must not be guessed from connectivity resemblance. Registered as a correction in `PART2-ID-SETS.md` §7 (added 24 Nov 2026) and in the Part 0 register (G2); the frozen `id_sets_v1` artefacts are **not** changed, and nothing was re-run.
- **aDN1: undetermined from the project data.** Every source names it `id_DN1_1` — a numeric suffix, no side marker. Whether aDN1 is a bilateral pair or a single neuron cannot be settled from what is on disk; it is recorded as undetermined, resolvable by the same crosswalk route. The Part 2b loop as built is unaffected either way (aDN1 enters the decoder's pool as one neuron; a right aDN1, if one exists and were ever added, would enter the same pool).

### 10.4 One long episode — 15 s closed loop, criteria fixed before the run (condition (c))

The battery's STABLE verdict covers 2 s episodes; Reviewer 1's caveat was that 2 s says nothing about long-run robustness.
